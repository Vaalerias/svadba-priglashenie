# DATA_MODEL.md

Проект стартует в локальном режиме. Записи живут в браузере текущего устройства.

## Универсальная запись

- `id` — уникальный идентификатор.
- `record_type` — тип: заявка, результат квиза, клиент или задача.
- `payload` — полезные поля конкретной записи.
- `status` — текущий этап.
- `created_at` — дата создания.
- `updated_at` — дата изменения.
- `archived_at` — дата архивации.

## Владелец данных

До подключения базы локальные записи видит только этот браузер.

После подключения Supabase записи принадлежат `workspace_id`. Читать и менять их может участник рабочей области. Публичная форма может только создать ограниченный тип записи.

## Демонстрационный ответ семьи

Локальная запись ответа использует тип `family_response`. В одном браузере хранится одна активная запись на один семейный код из личной ссылки: повторное сохранение с тем же кодом обновляет её. Старые демонстрационные записи типа `lead` продолжают читаться на рабочем экране.

В `payload` хранятся:

- `first_name` — вымышленное имя отвечающего;
- `last_name` — вымышленная фамилия отвечающего;
- `attendance` — `attending` или `declined`;
- `guest_count` — количество взрослых и детей, при отказе `0`;
- `participants` — список участников с `first_name` и `last_name`, при отказе пустой список.
- `family_code` — код семьи из личной ссылки. Он отделяет демонстрационные ответы в браузере и определяет строку семьи в подготовленной Google Таблице.

Поля `name`, `contact` и `problem` временно дублируются для совместимости с рабочим экраном. При отказе данные сохраняются только после заполнения имени и фамилии. При согласии количество должно совпадать с числом участников, у каждого нужны имя и фамилия.

Опубликованный обработчик записывает и обновляет одну строку на семейный код в подготовленной Google Таблице. Сайт обращается к нему после проверки формы и показывает благодарность только после подтверждения записи.

## Не храним

- платёжные данные карты;
- пароли;
- паспортные данные;
- секретные ключи;
- лишние личные сведения «на будущее».
