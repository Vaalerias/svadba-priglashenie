# Путь для продукта с пользователями из России

## Главное решение

Облачный Supabase удобен для обучения и прототипов. Его управляемые регионы находятся за пределами России.

Если продукт собирает персональные данные граждан РФ, не делай зарубежный Supabase единственной первичной базой. Проверь требования 152-ФЗ с профильным юристом.

## Три безопасных уровня

**Уровень 1 — учебный.** Локальный режим и вымышленные данные. Подходит всему курсу до публикации.

**Уровень 2 — демонстрационный.** Hosted Supabase с тестовыми или обезличенными данными. Быстро, но не считаем российским production-контуром.

**Уровень 3 — production в РФ.** База и первичная обработка в российской инфраструктуре. Возможные схемы:

- self-hosted Supabase на российском VPS;
- сервер приложения в Yandex Cloud + Managed PostgreSQL;
- другой российский облачный провайдер с PostgreSQL и резервными копиями.

## Почему self-hosted Supabase не ставим в первый модуль

Полный стек требует Docker, домен, HTTPS, резервные копии, обновления и заметный объём ресурсов. Это задача администратора или отдельного продвинутого воркшопа.

## Рекомендуемая архитектура AIRC

```text
Статический интерфейс
        ↓
серверный API в российском облаке
        ↓
PostgreSQL в российском регионе
        ↓
Object Storage для файлов
```

Секреты хранятся на сервере. Браузер получает только публичную конфигурацию.

## Промпт для агента

```text
Изучи текущий проект и DATA_MODEL.md.
Нужно подготовить production-план для пользователей из РФ.

Требования:
— первичная база с персональными данными находится в России;
— браузер не получает секреты;
— есть резервные копии и экспорт;
— есть отдельные development, preview и production;
— миграция не удаляет существующие данные;
— список внешних сервисов и трансграничных передач зафиксирован.

Сначала верни архитектуру, риски, ручные шаги и стоимость компонентов.
Код и облачные ресурсы пока не создавай.
```
